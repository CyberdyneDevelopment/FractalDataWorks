# TypeCollection Patterns in FractalDataWorks

This guide explains the two primary TypeCollection patterns in FractalDataWorks: **ServiceTypeCollection** for service plugins and **MutableTypeCollection** for configuration registries.

Only **ServiceTypeCollection** is itself DI-integrated — its three-phase `Configure`/`Register`/`Initialize` methods are auto-generated **on the collection class** by `Collections.SourceGenerators`. A **MutableTypeCollection** (like a plain `TypeCollection`) is a bare type registry with **no DI orchestration of its own**. Its option set is populated at load time by module initializers / generated static constructors calling `RegisterMember` (see [Cross-Assembly Registration via Module Initializers](#cross-assembly-registration-via-module-initializers)), which is a **separate mechanism from three-phase DI**. A MutableTypeCollection domain MAY *additionally* have a **hand-written sibling Provider class** (e.g. `DataSetProvider`, `ConfigurationGatewayDataStoreProvider`) that carries the three-phase methods — but the methods live on the *Provider*, never on the collection, and many MutableTypeCollections (e.g. `PropertyRoles`, `DataLayouts`) have no DI at all. A sibling Provider joins the `PlatformServices` sweep by carrying the `[PlatformServiceProvider]` attribute.

## Overview

FractalDataWorks provides two patterns for managing collections of types:

| Pattern | Use Case | Examples |
|---------|----------|----------|
| ServiceTypeCollection | Services with behavior (register themselves) | ConnectionTypes, AuthenticationServiceTypes, EtlPipelineTypes |
| MutableTypeCollection | Configuration registries (optional sibling Provider carries any DI) | DataSetTypes (+ DataSetProvider), DataStoreTypes (+ ConfigurationGatewayDataStoreProvider), PropertyRoles, DataLayouts |

## Pattern 1: ServiceTypeCollection - For Services with Behavior

Use **ServiceTypeCollection** when:
- Types have behavior (methods beyond getters)
- Each type registers its own services
- Types are compile-time discovered "plugins" that add capabilities

### Characteristics

- Types register their own services via `RegisterRequiredServices(IServiceCollection)` method
- Auto-generated provider aggregates all type registrations
- Three-phase registration is auto-generated by source generator
- Types define HOW services work (factories, executors, etc.)

### Anatomy — Reference: ConnectionTypes

A ServiceTypeCollection has four required components. All four must have matching generic type parameter counts. The reference implementation is ConnectionTypes (3 domain type parameters: TService, TFactory, TConfiguration).

#### 1. Interface — `*.Abstractions` package

Two interfaces: a generic variant with full type parameters extending `IServiceType<Guid, ...>`, and a non-generic marker extending `IServiceType`.

```csharp
// Fdw.Services.Connections.Abstractions/IConnectionType.cs

// Generic interface — carries the type parameters
public interface IConnectionType<TService, TConfiguration, TFactory>
    : IServiceType<Guid, TService, TFactory, TConfiguration>, IConnectionType
    where TService : IGenericConnection
    where TConfiguration : IConnectionConfiguration
    where TFactory : IConnectionFactory<TService, TConfiguration>
{
}

// Non-generic marker — used by the collection class
public interface IConnectionType : IServiceType
{
}
```

#### 2. Base class — main domain package

The base class keeps type parameters **open**. Each concrete option resolves them to unique types, which gives every option a unique `Id`.

```csharp
// Fdw.Services.Connections/ConnectionTypeBase.cs

public abstract class ConnectionTypeBase<TService, TFactory, TConfiguration>
    : ServiceTypeBase<TService, TFactory, TConfiguration, DefaultConnectionProvider>,
      IConnectionType<TService, TConfiguration, TFactory>,
      ISchemaDiscovery
    where TService : IGenericConnection
    where TConfiguration : class, IConnectionConfiguration
    where TFactory : IConnectionFactory<TService, TConfiguration>
{
    protected ConnectionTypeBase(
        string name, string sectionName,
        string displayName, string description,
        string? category = null)
        : base(name, sectionName, displayName, description, category ?? "Connection")
    {
    }
}
```

**Why open generics matter:** `ServiceTypeBase<TService, TFactory>.Id` computes a deterministic GUID from `typeof(TService).FullName` + `typeof(TFactory).FullName`. If the base class closes these parameters (e.g., `ServiceTypeBase<IGenericService, IServiceFactory<IGenericService>>`), then **every derived type gets the same Id** and only the first one survives `RegisterMember()` deduplication. This silently drops all other options from the collection.

#### 3. Collection class — main domain package

The `[ServiceTypeCollection]` attribute takes three positional arguments plus named properties. The class inherits `ServiceTypeCollectionBase<TBase, TInterface>` where both type arguments use the **closed generic form** of the base class and interface (closing over the most general constraint types).

```csharp
// Fdw.Services.Connections/ConnectionTypes.cs

[ServiceTypeCollection(
    typeof(ConnectionTypeBase<IGenericConnection,
        IConnectionFactory<IGenericConnection, IConnectionConfiguration>,
        IConnectionConfiguration>),
    typeof(IConnectionType),
    typeof(ConnectionTypes),
    GenerateProvider = true,
    ServiceInterface = typeof(IGenericConnection),
    ConfigurationInterface = typeof(IConnectionConfiguration),
    ConfigurationType = typeof(ConnectionConfiguration),
    ProviderType = typeof(DefaultConnectionProvider),
    ProviderInterface = typeof(IConnectionProvider),
    ServiceCategory = "Connection")]
public partial class ConnectionTypes : ServiceTypeCollectionBase<
    ConnectionTypeBase<IGenericConnection,
        IConnectionFactory<IGenericConnection, IConnectionConfiguration>,
        IConnectionConfiguration>,
    IConnectionType<IGenericConnection, IConnectionConfiguration,
        IConnectionFactory<IGenericConnection, IConnectionConfiguration>>>
{
}
```

**Attribute arguments:**

| Argument | Value | Purpose |
|----------|-------|---------|
| `arg[0]` (BaseType) | `typeof(ConnectionTypeBase<...>)` closed | Base class with general constraint types |
| `arg[1]` (InterfaceType) | `typeof(IConnectionType)` | Non-generic marker interface |
| `arg[2]` (CollectionType) | `typeof(ConnectionTypes)` | This collection class |
| `GenerateProvider` | `true` | Source generator creates provider registration |
| `ServiceInterface` | `typeof(IGenericConnection)` | The service contract |
| `ConfigurationInterface` | `typeof(IConnectionConfiguration)` | The configuration contract |
| `ConfigurationType` | `typeof(ConnectionConfiguration)` | Concrete configuration class |
| `ProviderType` | `typeof(DefaultConnectionProvider)` | Provider implementation |
| `ProviderInterface` | `typeof(IConnectionProvider)` | Provider interface |
| `ServiceCategory` | `"Connection"` | Database configuration category |

#### 4. Concrete options — per-implementation packages

Each option resolves all type parameters to specific types, giving it a unique identity.

```csharp
// Fdw.Services.Connections.MsSql/MsSqlConnectionType.cs

[ServiceTypeOption(typeof(ConnectionTypes), "MsSql")]
public sealed class MsSqlConnectionType
    : ConnectionTypeBase<IGenericConnection, IMsSqlConnectionFactory, MsSqlConnectionConfiguration>
{
    public MsSqlConnectionType()
        : base("MsSql", "Connections:MsSql", "Microsoft SQL Server",
               "SQL Server connection provider") { }

    public override void Configure(IServiceCollection services, IConfiguration configuration)
    {
        // Register named HttpClient, bind IOptions, etc.
    }

    public override IServiceCollection RegisterRequiredServices(IServiceCollection services)
    {
        // Register factory, services
        return services;
    }

    public override void RegisterFactory(DefaultConnectionProvider provider, IServiceProvider services)
    {
        // Register factory with the provider
    }
}
```

### Package Structure

Each ServiceTypeCollection domain follows this package layout:

```
Fdw.Services.{Domain}.Abstractions/
    I{Domain}Type.cs              — Generic + marker interfaces
    I{Domain}Configuration.cs     — Configuration interface
    I{Domain}Provider.cs          — Provider interface
    IGeneric{Domain}.cs           — Service interface

Fdw.Services.{Domain}/
    {Domain}Types.cs              — [ServiceTypeCollection] class
    {Domain}TypeBase.cs           — Open-generic base class
    Default{Domain}Provider.cs    — Provider implementation
    {Domain}Configuration.cs      — Configuration record

Fdw.Services.{Domain}.{Implementation}/
    {Impl}{Domain}Type.cs         — [ServiceTypeOption] concrete option
    {Impl}{Domain}Configuration.cs — Implementation-specific config
```

### Type Parameter Count Rule

All four components must agree on the number of domain type parameters:

| Component | ConnectionTypes (3 params) |
|-----------|--------------------------|
| Interface | `IConnectionType<TService, TConfiguration, TFactory>` |
| Base class | `ConnectionTypeBase<TService, TFactory, TConfiguration>` |
| Collection attribute arg[0] | `typeof(ConnectionTypeBase<IGenericConnection, IConnectionFactory<...>, IConnectionConfiguration>)` |
| Concrete option | `MsSqlConnectionType : ConnectionTypeBase<IGenericConnection, IMsSqlConnectionFactory, MsSqlConnectionConfiguration>` |

Each concrete option resolves at least one type parameter to a **unique type** (typically the factory or configuration), ensuring a unique `Id`.

### Cross-Assembly Registration via Module Initializers

Concrete options typically live in separate packages from the collection (e.g., `MsSqlConnectionType` in `Services.Connections.MsSql`, while `ConnectionTypes` is in `Services.Connections`). The `Fdw.Registration.SourceGenerators` package generates `[ModuleInitializer]` methods that call `RegisterMember()` before any user code runs.

**The generator is referenced only by entry point projects** (executables like `Reference.Api`, `Reference.UI`). When the entry point compiles, the generator scans all referenced assemblies for `[ServiceTypeOption]` types and emits a single `[ModuleInitializer]` in the executable that registers every discovered option with its collection.

```csharp
// Auto-generated in the entry point project (e.g., Reference.Api)
[ModuleInitializer]
internal static void Initialize()
{
    // Register with ConnectionTypes
    ConnectionTypes.RegisterMember(new MsSqlConnectionType());
    ConnectionTypes.RegisterMember(new PostgreSqlConnectionType());

    // Register with AuthenticationServiceTypes
    AuthenticationServiceTypes.RegisterMember(new OpenIddictAuthenticationType());

    // Register with ApiClientTypes
    ApiClientTypes.RegisterMember(new PipelineClientType());
    ApiClientTypes.RegisterMember(new ConnectionClientType());
    // ... every [ServiceTypeOption] found across all referenced assemblies
}
```

**Entry point requirement:** The entry point `.csproj` must reference `Fdw.Registration.SourceGenerators` as an analyzer. Without it, the module initializer is never generated and cross-assembly options are never registered.

```xml
<!-- In the entry point .csproj (Reference.Api, Reference.UI, etc.) -->
<ItemGroup>
  <PackageReference Include="Fdw.Registration.SourceGenerators"
                    OutputItemType="Analyzer" ReferenceOutputAssembly="false" />
</ItemGroup>
```

**Worked example — package reference IS the registration intent:**

`Fdw.Services.Credentials.Sql` contributes the SQL credential service (with vault-backed PAT and agent-key services) to `CredentialServiceTypes` without any app-side code:

```csharp
// Services.Credentials.Sql/Registration/SqlCredentialServiceType.cs

[ServiceTypeOption(typeof(CredentialServiceTypes), "Sql")]
public sealed class SqlCredentialServiceType : CredentialServiceTypeBase<…>
{
    // Configure: binds List<SqlCredentialServiceConfiguration> + CredentialsSqlOptions (selector)
    // RegisterRequiredServices: registers the credential service factory + typed body provider,
    //                           vault-backed PAT + agent-key services (Scoped),
    //                           IAgentKeyVaultCommands (Singleton), hashing primitives (Singleton)
}
```

When the entry-point project adds `<PackageReference Include="Fdw.Services.Credentials.Sql" />`, the source generator emits `CredentialServiceTypes.RegisterMember(new SqlCredentialServiceType())` in the executable's module initializer. The app's existing `CredentialServiceTypes.Configure/Register/Initialize` calls invoke the three phases — zero app registration code. (This replaced the earlier graft that registered SQL credentials as a cross-assembly option of the restricted `UserServiceTypes`.)

**Deferred freeze pattern:** `RegisterMember()` adds to a pending list. On first access to `All()`, `Configure()`, or `Register()`, the collection freezes into a `FrozenDictionary`. Calling `RegisterMember()` after freeze throws `InvalidOperationException`.

### Entry Point Usage

```csharp
// Phase 1a: Configure (before Build)
ConnectionTypes.Configure(builder, loggerFactory);

// Phase 1b: Register (before Build)
ConnectionTypes.Register(builder.Services, loggerFactory);

var app = builder.Build();

// Phase 2: Initialize (after Build)
ConnectionTypes.Initialize(app.Services, loggerFactory);
```

### Overriding a phase — the mutable `Configuration` / `Registration` / `Initialization` methods

Each generated `Configure` / `Register` / `Initialize` is now a **thin invoker over a swappable static
delegate field** whose *default value is the generated body*. So every ServiceTypeCollection also
carries a noun-named setter to replace that phase at runtime:

```csharp
// generated on ConnectionTypes (shape is identical for Configuration / Initialization):
private static Action<IServiceCollection, ILoggerFactory?> RegistrationMethod =
    static (services, loggerFactory) => { /* the generated Register body — the DEFAULT */ };

public static void Registration(Action<IServiceCollection, ILoggerFactory?> customFunc)   // ← override
    => RegistrationMethod = customFunc;

public static void Register(IServiceCollection services, ILoggerFactory? loggerFactory = null)  // ← invoke
    => RegistrationMethod(services, loggerFactory);
```

A host — or the collection author via a curated `UseXxx()` wrapper — can **replace any or all of the
three phase methods**. Call the setter **before** that phase's sweep:

```csharp
// Program.cs, before PlatformServices.Register / Build():
ConnectionTypes.Configuration((builder, lf) => { /* custom configure */ return builder; });
ConnectionTypes.Registration((services, lf) => { /* custom register  */ });
ConnectionTypes.Initialization((sp, lf) => { /* custom initialize */ });
```

Rules:

- **Default preserved.** A collection you never touch behaves exactly as before — the field holds the generated body.
- **Lock-at-sweep.** Set the override *before* the phase runs. Once `PlatformServices.Configure/Register/Initialize` (or a dot-walked `PlatformServices.Connection?.Register(...)`) has run that phase, the invoker simply runs whatever the field currently holds.
- **Front door = author-curated variant.** The blessed pattern is a collection exposing a named method (e.g. `UseThinClient()`) that calls its *own* `Registration(...)` with a delegate the author wrote — registration stays FDW-owned. The raw setter is the escape hatch.
- Because override is a runtime setter, you **no longer hand-write a static phase method in the partial class to override it** — the old "define the method with the exact signature and the generator skips it" trick is superseded.

## Pattern 2: MutableTypeCollection - For Configuration Registries

Use **MutableTypeCollection** when:
- Types represent configuration/data, not behavior
- A central Provider manages registration
- Configurations are loaded from IOptions (database or JSON)
- Runtime registration of new instances is needed

### Characteristics

- The collection itself is a **bare** `[MutableTypeCollection]` — no `Configure`/`Register`/`Initialize` on the collection class. Its options are populated by module-init / static-ctor `RegisterMember` at load time.
- A domain that needs DI (e.g. DataSet, DataStore) adds a **hand-written sibling Provider class** that carries the static three-phase `Configure`/`Register`/`Initialize` methods.
- That Provider is what gets registered in DI during its `Register()` phase, and what merges compile-time collection members with runtime configuration records at read time.
- Domains that need **no** DI (e.g. `PropertyRoles`, `DataLayouts`) are pure compile-time collections with no Provider and no three-phase methods at all.

### Example 1: DataSetTypes (bare collection) + DataSetProvider (three-phase)

The collection is **bare**. It carries the options and a `ServiceCategory` — there are **no** `Configure`/`Register`/`Initialize` methods on it. (Source: `Fdw.Data.DataSets.Abstractions/DataSetTypes.cs`.)

```csharp
// Fdw.Data.DataSets.Abstractions/DataSetTypes.cs
//
// Pure type collection with no DI orchestration.
// DI registration is handled by DataSetProvider.
// [MutableTypeCollection] is used (not [TypeCollection]) to support cross-assembly
// TypeOption registration (e.g. WorkflowDefinitionsDataSet in Orchestration.Workflows).
[MutableTypeCollection(typeof(DataSetTypeBase), typeof(IDataSetType), typeof(DataSetTypes))]
public abstract partial class DataSetTypes : TypeCollectionBase<DataSetTypeBase, IDataSetType>
{
    // The service category for database configuration loading.
    public static string ServiceCategory => "DataSet";
    // No Configure/Register/Initialize here — see DataSetProvider below.
}
```

The three-phase DI methods live on the **hand-written sibling Provider class** `DataSetProvider`, in the core package. (Source: `Fdw.Services.Data/DataSetProvider.cs`.)

```csharp
// Fdw.Services.Data/DataSetProvider.cs

public sealed class DataSetProvider : IDataSetConfigurationProvider
{
    // Phase 1a: Configure — takes the host builder, returns it for chaining.
    public static TBuilder Configure<TBuilder>(TBuilder builder, ILoggerFactory? loggerFactory = null)
        where TBuilder : IHostApplicationBuilder
    {
        // Startup diagnostics only; no IOptions boot-binding of dataset instances.
        return builder;
    }

    // Phase 1b: Register — registers the gateway-backed config provider, factory, and runtime provider.
    public static void Register(IServiceCollection services, ILoggerFactory? loggerFactory = null)
    {
        DataSetConfigurationProvider.RegisterDomainConfiguration(services);
        services.TryAddSingleton<IDataSetConfigurationProvider>(sp => new DataSetProvider(/* … */));
        services.TryAddSingleton<IDataSetFactory>(sp => new DataSetFactory(/* … */));
        services.TryAddSingleton<IDataSetProvider>(sp => new DataSetRuntimeProvider(/* … */));
    }

    // Phase 2: Initialize — DOES NOT stuff config instances into DataSetTypes.
    public static void Initialize(IServiceProvider services, ILoggerFactory? loggerFactory = null)
    {
        // Why: DataSetTypes holds the static strategy KINDS (Simple/Compound/Federated) — it is NOT a
        // registry of dataset instances. Instances are resolved live from the configuration provider;
        // DataGatewayService dispatches on the authored ServiceOptionType. No per-instance registration
        // happens here.
    }
}
```

**The old boot loop was deleted.** Earlier revisions of this doc showed `Initialize` iterating `IOptions<List<DataSetConfiguration>>` and calling `provider.RegisterDataSet(config.Name, config)` to stuff each configured dataset **into** `DataSetTypes`. That loop was removed because it **froze runtime-created datasets out of execution** — datasets created after startup were never in the collection. Dataset instances are now read live from the configuration provider (`IServiceConfigurationProvider<DataSetConfiguration>` over ConfigurationDb); `DataSetTypes` retains only the code-defined strategy kinds.

### Example 2: PropertyRoles (Schema Metadata)

PropertyRoles is a simpler MutableTypeCollection that doesn't require a provider or IOptions binding. It's purely a compile-time collection of schema metadata.

```csharp
[MutableTypeCollection(typeof(PropertyRoleBase), typeof(IPropertyRole), typeof(PropertyRoles))]
public abstract partial class PropertyRoles : TypeCollectionBase<PropertyRoleBase, IPropertyRole>
{
    // No Configure/Register/Initialize - purely compile-time discovery
}

// TypeOptions define the roles
[TypeOption(typeof(PropertyRoles), "Surrogate")]
public sealed class SurrogateRole : PropertyRoleBase
{
    public SurrogateRole()
        : base(
            id: 1,
            name: "Surrogate",
            description: "Auto-generated key with no business meaning",
            isKeyRole: true,
            isIndexable: true,
            isAggregatable: false)
    {
    }
}

[TypeOption(typeof(PropertyRoles), "Measure")]
public sealed class MeasureRole : PropertyRoleBase
{
    public MeasureRole()
        : base(
            id: 5,
            name: "Measure",
            description: "Numeric value for aggregation",
            isKeyRole: false,
            isIndexable: false,
            isAggregatable: true)
    {
    }
}
```

**Usage:**
```csharp
// No switch statements needed - roles know their properties!
var property = new PropertyDefinition
{
    Name = "TotalSales",
    Role = PropertyRoles.Measure  // Generated static property
};

if (property.Role.IsAggregatable)
{
    // SUM(TotalSales), AVG(TotalSales), etc.
    GenerateAggregateQuery(property);
}

// Get all key fields from a schema
var keyFields = schema.Properties
    .Where(p => p.Role.IsKeyRole)
    .ToList();
```

### Example 3: DataLayouts (Schema Structure Metadata)

DataLayouts describes the structural characteristics of data (tabular, hierarchical, etc.) without needing runtime registration.

```csharp
[MutableTypeCollection(typeof(DataLayoutBase), typeof(IDataLayout), typeof(DataLayouts))]
public abstract partial class DataLayouts : TypeCollectionBase<DataLayoutBase, IDataLayout>
{
    // No Configure/Register/Initialize - purely compile-time discovery
}

// TypeOptions define the layouts
[TypeOption(typeof(DataLayouts), "Tabular")]
public sealed class TabularLayout : DataLayoutBase
{
    public TabularLayout()
        : base(
            id: 1,
            name: "Tabular",
            description: "Flat rows and columns (SQL table, CSV, Excel)",
            supportsNesting: false,
            supportsFlattening: false,  // Already flat
            isTabular: true)
    {
    }
}

[TypeOption(typeof(DataLayouts), "Hierarchical")]
public sealed class HierarchicalLayout : DataLayoutBase
{
    public HierarchicalLayout()
        : base(
            id: 2,
            name: "Hierarchical",
            description: "Nested parent-child structure (JSON, XML)",
            supportsNesting: true,
            supportsFlattening: true,
            isTabular: false)
    {
    }
}
```

**Usage:**
```csharp
// No switch statements - layouts know their properties!
var schema = new SchemaDefinition
{
    Name = "OrderWithLineItems",
    Layout = DataLayouts.Hierarchical  // Generated static property
};

if (schema.Layout.SupportsNesting)
{
    ProcessChildSchemas(schema.Children);
}

if (schema.Layout.IsTabular)
{
    GenerateSqlDdl(schema);  // Only for tabular layouts
}

if (schema.Layout.SupportsFlattening)
{
    var flattenedSchema = FlattenToTabular(schema);
}
```

### Entry Point Usage

The three-phase methods live on the **Provider** classes (`DataSetProvider`,
`ConfigurationGatewayDataStoreProvider`), not on the `*Types` collections — the collections expose no
such methods. Because each Provider carries `[PlatformServiceProvider]`, the entry point does **not**
call them by hand; the single `PlatformServices` sweep invokes them in Group order alongside
every `[ServiceTypeCollection]` domain:

```csharp
// Phase 1: Configure + Register (before Build) — ONE sweep drives every
// [ServiceTypeCollection] AND every [PlatformServiceProvider] sibling Provider.
PlatformServices.Configure(builder, loggerFactory);
PlatformServices.Register(builder.Services, loggerFactory);

var app = builder.Build();

// Phase 2: Initialize (after Build) — ONE sweep. Container registration is folded INTO
// ConfigurationGatewayDataStoreProvider.Initialize (blocked-on once at startup), not a separate call.
PlatformServices.Initialize(app.Services, loggerFactory);

// PropertyRoles and DataLayouts have no Provider and no registration — compile-time only.
```

## Decision Tree

```
Does the type have behavior (Register method)?
├── YES → ServiceTypeCollection
│         • Types register their own services
│         • Auto-generated provider aggregates registrations
│         • Examples: ConnectionTypes, AuthenticationServiceTypes, EtlPipelineTypes
│
└── NO  → MutableTypeCollection (bare collection)
          • Collection itself has no DI; options arrive via module-init / static-ctor RegisterMember
          • If the domain needs DI, a hand-written sibling Provider carries Configure/Register/Initialize
          • Pure-metadata collections (PropertyRoles, DataLayouts) have no Provider at all
          • Examples: DataSetTypes (+ DataSetProvider), DataStoreTypes (+ ConfigurationGatewayDataStoreProvider), PropertyRoles
```

**Note:** `DataStoreTypes` is a **bare** `[MutableTypeCollection]` (no methods beyond a `ServiceCategory` property). Its child-configuration binding and container registration live on the hand-written sibling `ConfigurationGatewayDataStoreProvider` class (`[PlatformServiceProvider(ServiceCategory = "DataStore", Group = 8)]`), which carries the static `Configure`/`Register`/`Initialize` methods — container registration is folded into `ConfigurationGatewayDataStoreProvider.Initialize` (blocked-on once at startup), not a separate `RegisterContainers` method. That server-side provider delegates all connection-agnostic store composition to the pure `ConfiguredDataStoreProvider` core (see [05-03 DataNode Core Split](05-03-DataNode-Core-Split.md)). (Source: `Fdw.Services.Data.Abstractions/DataStoreTypes.cs`, `Fdw.Services.Data/ConfigurationGatewayDataStoreProvider.cs`.)

## Three-Phase Registration Pattern

**Not all TypeCollections have three phases.** Two distinct mechanisms are in play, and it is important to keep them separate:

1. **Populating the option set** — every TypeCollection (plain `TypeCollection`, `MutableTypeCollection`, or `ServiceTypeCollection`) gets its members via `RegisterMember`, called by **module initializers** (cross-assembly options) and **generated static constructors** (co-located options). This is a load-time mechanism and is **not** three-phase DI. See [Cross-Assembly Registration via Module Initializers](#cross-assembly-registration-via-module-initializers).

2. **Three-phase DI (`Configure`/`Register`/`Initialize`)** — a *separate* mechanism that applies only to:
   - **`ServiceTypeCollection`s**, where the three phases are **auto-generated on the collection class** (e.g. `ConnectionTypes.Configure/Register/Initialize`), and
   - **hand-written domain Provider classes** that accompany a `MutableTypeCollection` (e.g. `DataSetProvider`, `DataStoreProvider`). The methods live on the **Provider**, never on the collection.

A plain `TypeCollection` and most `MutableTypeCollection`s (e.g. `PropertyRoles`, `DataLayouts`) have **no** `Configure`/`Register`/`Initialize` at all — they are populated purely by module-init / static-ctor `RegisterMember` and consumed as compile-time metadata.

The three phases below therefore describe **ServiceTypeCollections and domain Provider classes only**:

Call these on a **ServiceTypeCollection** (e.g. `ConnectionTypes`) or on a **domain Provider** (e.g. `DataSetProvider`) — the placeholder `DomainTarget` below stands for whichever applies.

### Phase 1a: Configure (Before Build)

Binds `IOptions<T>` / performs startup configuration. `Configure` takes the host builder and returns it. Call before `builder.Build()`.

```csharp
DomainTarget.Configure(builder, loggerFactory);
```

### Phase 1b: Register (Before Build)

Registers services with the DI container. Call before `builder.Build()`.

```csharp
// Registers providers, factories, and infrastructure services
DomainTarget.Register(builder.Services, loggerFactory);
```

### Phase 2: Initialize (After Build)

Resolves services and performs runtime initialization. Call after `builder.Build()`.

```csharp
var app = builder.Build();

// Eagerly resolves provider, validates setup
DomainTarget.Initialize(app.Services, loggerFactory);
```

## Registration Order

Service domains have dependencies. The `PlatformServices` sweep encodes this order via each
domain's `Group` number (lower runs first), so an entry-point app no longer sequences these calls by
hand — but the underlying dependency order is unchanged:

1. **SecretManagers** - No dependencies
2. **Connections** - Depends on SecretManagers
3. **Authentication** - Depends on Connections
4. **Pipelines/ETL** - Depends on Connections, Authentication
5. **Data (DataSets, DataStores)** - Depends on Connections

## Anti-Patterns: What NOT to Do

> The examples below show the three-phase **contract each domain Provider still implements**
> (`Configure`/`Register`/`Initialize`, in order, via its own `Register` phase — never a manual
> `AddSingleton`). In current apps these are invoked for you by the single `PlatformServices`
> sweep (see [12-01 Creating a Server](12-01-Creating-A-Server.md)), not called by hand in
> `Program.cs` — the anti-patterns below are what the sweep itself must avoid internally, and
> what a domain author must still get right when implementing a new Provider's three phases.

### Don't Use ConfigurationLoader Directly

```csharp
// WRONG - Using ConfigurationLoader in entry point
var loader = new ConfigurationLoader(...);  // Now internal
await loader.LoadAll();

// CORRECT - Use the domain Provider's three-phase methods
DataSetProvider.Configure(builder, loggerFactory);
DataSetProvider.Register(builder.Services, loggerFactory);
DataSetProvider.Initialize(app.Services, loggerFactory);
```

### Don't Skip Phases

```csharp
// WRONG - Skipping Configure phase
DataSetProvider.Register(builder.Services, loggerFactory);
DataSetProvider.Initialize(app.Services, loggerFactory);

// CORRECT - All three phases in order
DataSetProvider.Configure(builder, loggerFactory);
DataSetProvider.Register(builder.Services, loggerFactory);
DataSetProvider.Initialize(app.Services, loggerFactory);
```

### Don't Register Providers Manually

```csharp
// WRONG - Manual provider registration outside the Provider's three-phase methods
services.AddSingleton<IDataSetProvider, DataSetProvider>();

// CORRECT - Let the domain Provider's Register phase wire it up
DataSetProvider.Register(builder.Services, loggerFactory);
```

## Creating New Configuration Registries

When creating a new configuration registry (MutableTypeCollection pattern):

1. **Create the configuration class** implementing `IGenericConfiguration`
2. **Create the provider interface** (e.g., `IFooProvider`)
3. **Create the provider implementation** (e.g., `FooProvider`)
4. **Create the MutableTypeCollection** — a **bare** `[MutableTypeCollection]` with **no** Configure/Register/Initialize (options arrive via module-init / static-ctor `RegisterMember`)
5. **Add the static three-phase methods to the Provider class** (`FooProvider.Configure`/`.Register`/`.Initialize`) — only if the domain needs DI; pure metadata collections (like `PropertyRoles`) skip this entirely
6. **Add to entry point registration** in correct order, calling the methods **on the Provider** (`FooProvider.Configure(...)`), not on the collection

Use the `/register-provider` Claude Code skill to automate this process.

## Service-Options and the Provider-Injection Contract

A `ServiceTypeCollection` exists so consumers never touch a concrete service directly — they resolve one **by name** through the generated `IFdwServiceProvider<TService, TConfiguration>`. Four framework pieces make that contract explicit and enforce it at build time.

### The `IServiceOption` marker

`Fdw.Services.Abstractions.IServiceOption : IGenericService` marks a service interface as **the `ServiceInterface` of a `[ServiceTypeCollection]`** — i.e. a service that HAS a provider and must be resolved through it.

```csharp
// Source: Fdw.Services.Abstractions/IServiceOption.cs
public interface IServiceOption : IGenericService { }

// A domain's service interface opts in by extending it:
public interface ITokenManager : IServiceOption { /* Issue/Validate/... */ }
```

- It is applied to **exactly** the interfaces used as a `[ServiceTypeCollection].ServiceInterface` — **not** to every `IGenericService`. Only provider-backed services are marked: `ISecretManager`, `ITokenManager`, `ICredentialService`, `IDataVault`, `IPipeline` (and `IEtlPipeline`), `IGenericConnection`, `IGenericNotification`, `IGenericTransformation`, `IGenericWorkflow`, `IHealthMonitorService`, `IFrameworkSchedulingService`.
- The marker is **transitive**: any interface that extends a marked one is itself a service-option (detection flattens the whole interface graph via `AllInterfaces`).
- **Meaning:** "consumers must inject this service's `IFdwServiceProvider<TService, TConfiguration>` and resolve the concrete instance by name — never inject the service interface (or its implementation) directly."

### FDW044 — service-options inject providers, not services (Error)

`FDW044` (`ServiceProviderInjectionAnalyzer`, `Fdw.ServiceTypes.Analyzers`) enforces the marker's meaning. A class whose `AllInterfaces` contains `IServiceOption` **may not** take a constructor parameter that is itself an `IServiceOption`-typed interface — it must inject the provider indirection instead.

```csharp
// WRONG — a service-option injecting another service-option directly (FDW044)
public sealed class OpenIddictValidationKeyConfigurator
{
    public OpenIddictValidationKeyConfigurator(ISecretManager secretManager) { } // ← flagged
}

// CORRECT — inject the provider and resolve by name (the pattern already in code)
public sealed class OpenIddictValidationKeyConfigurator
{
    public OpenIddictValidationKeyConfigurator(
        IFdwServiceProvider<ISecretManager, SecretManagerConfiguration> secretManagerProvider) { }
}
```

- Detection is **semantic and transitive** (`AllInterfaces`), so it catches interfaces that transitively extend a marked `ServiceInterface`.
- `IFdwServiceProvider<...>` parameters (the arity-1/2/4 generic forms, namespace `Fdw.ServiceTypes`) are the **correct** shape and are excluded from the diagnostic.

### `[ServiceOptionDependency]` — the per-parameter opt-out

Occasionally the owning provider has already resolved the dependency **by name in system context** and hands it to an **immutable** service at construction. For that single case, mark the parameter with `[ServiceOptionDependency]` (`AttributeTargets.Parameter`) to opt it out of FDW044.

```csharp
// Source: Fdw.Services.Abstractions/ServiceOptionDependencyAttribute.cs
[AttributeUsage(AttributeTargets.Parameter, AllowMultiple = false, Inherited = false)]
public sealed class ServiceOptionDependencyAttribute : Attribute { }
```

- **Default (no attribute) = enforced.** The attribute is not a shortcut around injecting the provider — use it ONLY when the provider/factory supplies the dependency already-resolved.
- **Sole current use:** the DataVault chain. `DataVaultBase` / `MsSqlDataVaultBase` / `CredentialVault` each take `[ServiceOptionDependency] IDataConnection connection`; `DefaultDataVaultProvider` resolves that connection by name in system context (RLS-free) and `CredentialVaultFactory.Create` hands it to the immutable vault. (Source: `Fdw.Services.Credentials.Sql/`.)

### FDW024 — every `[ServiceTypeCollection]` carries the three phase methods (Error)

`FDW024` (`ServiceTypeCollectionPhaseMethodsAnalyzer`, `Fdw.ServiceTypes.Analyzers`) fails the build for a `[ServiceTypeCollection]` class that is missing any of the static three-phase methods:

- `Configure<TBuilder>(TBuilder, ILoggerFactory?)`
- `Register(IServiceCollection, ILoggerFactory?)`
- `Initialize(IServiceProvider, ILoggerFactory?)`

These are **ordinarily source-generated** into a partial by `ServiceTypeCollectionGenerator` — you do not hand-write them. The analyzer checks the merged `INamedTypeSymbol` (so it sees the generated partial's members). Its guarantee is what lets `PlatformServicesRegistrationGenerator` discover **every** `[ServiceTypeCollection]` into PlatformServices unconditionally, without a per-class existence check. Hand-written three-phase providers that aren't TypeCollections opt into the same discovery by carrying `[PlatformServiceProvider]` (e.g. `DataSetProvider`, `ConfigurationGatewayDataStoreProvider`, `RealTimeHubs`). FDW024 ships with a code fix (`ServiceTypeCollectionPhaseMethodsCodeFixProvider`) that inserts a missing method stub.

> Note the distinction drawn earlier in this guide: these three phase methods live **on the `[ServiceTypeCollection]` class** (auto-generated). A `[MutableTypeCollection]` is bare; when its domain needs DI, the three phases live on a **hand-written sibling Provider** (e.g. `DataSetProvider`) — and FDW024 does not apply to those Provider classes.
