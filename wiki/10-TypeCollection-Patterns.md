# TypeCollection Patterns in FractalDataWorks

This guide explains the two primary patterns for DI-integrated collections in FractalDataWorks: **ServiceTypeCollection** for service plugins and **MutableTypeCollection** for configuration registries.

## Overview

FractalDataWorks provides two patterns for managing collections of types that integrate with dependency injection:

| Pattern | Use Case | Examples |
|---------|----------|----------|
| ServiceTypeCollection | Services with behavior (register themselves) | ConnectionTypes, AuthenticationTypes, EtlPipelineTypes |
| MutableTypeCollection | Configuration registries (provider manages) | DataSetTypes, DataStoreTypes, PropertyRoles, DataLayouts |

## Pattern 1: ServiceTypeCollection - For Services with Behavior

Use **ServiceTypeCollection** when:
- Types have behavior (methods beyond getters)
- Each type registers its own services
- Types are compile-time discovered "plugins" that add capabilities

### Characteristics

- Types register their own services via `Register(IServiceCollection)` method
- Auto-generated provider aggregates all type registrations
- Three-phase registration is auto-generated by source generator
- Types define HOW services work (factories, executors, etc.)

### Example: ConnectionTypes

```csharp
[ServiceTypeCollection(
    typeof(ConnectionTypeBase<...>),
    typeof(IConnectionType),
    typeof(ConnectionTypes),
    GenerateProvider = true,
    ServiceInterface = typeof(IDataConnection),
    ConfigurationInterface = typeof(IConnectionConfiguration))]
public partial class ConnectionTypes : ServiceTypeCollectionBase<...> { }

// Each type registers itself:
[ServiceTypeOption(typeof(ConnectionTypes), "MsSql")]
public sealed class MsSqlConnectionType : ConnectionTypeBase<...>
{
    public override void Register(IServiceCollection services)
    {
        services.AddScoped<IMsSqlConnectionFactory, MsSqlConnectionFactory>();
    }
}
```

### Entry Point Usage

```csharp
// Phase 1a: Configure (before Build)
ConnectionTypes.Configure(services, configuration, loggerFactory);

// Phase 1b: Register (before Build)
ConnectionTypes.Register(services, loggerFactory);

var app = builder.Build();

// Phase 2: Initialize (after Build)
ConnectionTypes.Initialize(app.Services, loggerFactory);
```

## Pattern 2: MutableTypeCollection - For Configuration Registries

Use **MutableTypeCollection** when:
- Types represent configuration/data, not behavior
- A central Provider manages registration
- Configurations are loaded from IOptions (database or JSON)
- Runtime registration of new instances is needed

### Characteristics

- Central provider manages all registrations
- Provider is registered in DI during `Register()` phase
- Configurations loaded from `IOptions<List<TConfiguration>>` during `Initialize()`
- Supports both compile-time types AND runtime-loaded configurations

### Example 1: DataSetTypes (Provider-Managed Configuration)

```csharp
[MutableTypeCollection(
    typeof(DataSetConfigurationBase),
    typeof(IDataSetConfiguration),
    typeof(DataSetTypes))]
public abstract partial class DataSetTypes : TypeCollectionBase<...>
{
    // Phase 1a: Bind IOptions
    public static void Configure(IServiceCollection services, IConfiguration config, ILoggerFactory? loggerFactory)
    {
        services.Configure<List<DataSetConfiguration>>(config.GetSection("DataSets"));
    }

    // Phase 1b: Register provider
    public static void Register(IServiceCollection services, ILoggerFactory? loggerFactory)
    {
        services.TryAddSingleton<IDataSetProvider>(sp => new DataSetProvider(...));
    }

    // Phase 2: Load configs into provider
    public static void Initialize(IServiceProvider services, ILoggerFactory? loggerFactory)
    {
        var provider = services.GetRequiredService<IDataSetProvider>();
        RegisterAll(provider, logger);  // Compile-time types

        // Load IOptions configs from database
        var configured = services.GetService<IOptions<List<DataSetConfiguration>>>();
        if (configured?.Value != null)
        {
            foreach (var config in configured.Value.Where(c => !string.IsNullOrWhiteSpace(c.Name)))
            {
                provider.RegisterDataSet(config.Name, config);
            }
        }
    }
}
```

### Example 2: PropertyRoles (Schema Metadata)

PropertyRoles is a simpler MutableTypeCollection that doesn't require a provider or IOptions binding. It's purely a compile-time collection of schema metadata.

```csharp
[MutableTypeCollection(typeof(PropertyRoleBase), typeof(IPropertyRole), typeof(PropertyRoles))]
public abstract partial class PropertyRoles : TypeCollectionBase<PropertyRoleBase, IPropertyRole>
{
    // No Configure/Register/Initialize - purely compile-time discovery
}

// TypeOptions define the roles
[TypeOption(typeof(PropertyRoles), "Surrogate")]
public sealed class SurrogateRole : PropertyRoleBase
{
    public SurrogateRole()
        : base(
            id: 1,
            name: "Surrogate",
            description: "Auto-generated key with no business meaning",
            isKeyRole: true,
            isIndexable: true,
            isAggregatable: false)
    {
    }
}

[TypeOption(typeof(PropertyRoles), "Measure")]
public sealed class MeasureRole : PropertyRoleBase
{
    public MeasureRole()
        : base(
            id: 5,
            name: "Measure",
            description: "Numeric value for aggregation",
            isKeyRole: false,
            isIndexable: false,
            isAggregatable: true)
    {
    }
}
```

**Usage:**
```csharp
// No switch statements needed - roles know their properties!
var property = new PropertyDefinition
{
    Name = "TotalSales",
    Role = PropertyRoles.Measure  // Generated static property
};

if (property.Role.IsAggregatable)
{
    // SUM(TotalSales), AVG(TotalSales), etc.
    GenerateAggregateQuery(property);
}

// Get all key fields from a schema
var keyFields = schema.Properties
    .Where(p => p.Role.IsKeyRole)
    .ToList();
```

### Example 3: DataLayouts (Schema Structure Metadata)

DataLayouts describes the structural characteristics of data (tabular, hierarchical, etc.) without needing runtime registration.

```csharp
[MutableTypeCollection(typeof(DataLayoutBase), typeof(IDataLayout), typeof(DataLayouts))]
public abstract partial class DataLayouts : TypeCollectionBase<DataLayoutBase, IDataLayout>
{
    // No Configure/Register/Initialize - purely compile-time discovery
}

// TypeOptions define the layouts
[TypeOption(typeof(DataLayouts), "Tabular")]
public sealed class TabularLayout : DataLayoutBase
{
    public TabularLayout()
        : base(
            id: 1,
            name: "Tabular",
            description: "Flat rows and columns (SQL table, CSV, Excel)",
            supportsNesting: false,
            supportsFlattening: false,  // Already flat
            isTabular: true)
    {
    }
}

[TypeOption(typeof(DataLayouts), "Hierarchical")]
public sealed class HierarchicalLayout : DataLayoutBase
{
    public HierarchicalLayout()
        : base(
            id: 2,
            name: "Hierarchical",
            description: "Nested parent-child structure (JSON, XML)",
            supportsNesting: true,
            supportsFlattening: true,
            isTabular: false)
    {
    }
}
```

**Usage:**
```csharp
// No switch statements - layouts know their properties!
var schema = new SchemaDefinition
{
    Name = "OrderWithLineItems",
    Layout = DataLayouts.Hierarchical  // Generated static property
};

if (schema.Layout.SupportsNesting)
{
    ProcessChildSchemas(schema.Children);
}

if (schema.Layout.IsTabular)
{
    GenerateSqlDdl(schema);  // Only for tabular layouts
}

if (schema.Layout.SupportsFlattening)
{
    var flattenedSchema = FlattenToTabular(schema);
}
```

### Entry Point Usage

```csharp
// Phase 1a: Configure (before Build)
DataSetTypes.Configure(services, configuration, loggerFactory);
DataStoreTypes.Configure(services, configuration, loggerFactory);
TenantTypes.Configure(services, configuration, loggerFactory);

// Phase 1b: Register (before Build)
DataSetTypes.Register(services, loggerFactory);
DataStoreTypes.Register(services, loggerFactory);
TenantTypes.Register(services, loggerFactory);

var app = builder.Build();

// Phase 2: Initialize (after Build)
DataSetTypes.Initialize(app.Services, loggerFactory);
DataStoreTypes.Initialize(app.Services, loggerFactory);
TenantTypes.Initialize(app.Services, loggerFactory);

// PropertyRoles and DataLayouts don't need registration - compile-time only
```

## Decision Tree

```
Does the type have behavior (Register method)?
├── YES → ServiceTypeCollection
│         • Types register their own services
│         • Auto-generated provider aggregates registrations
│         • Examples: ConnectionTypes, AuthenticationTypes, EtlPipelineTypes
│
└── NO  → MutableTypeCollection
          • Central provider manages registrations
          • IOptions<List<T>> for database/JSON configurations
          • Examples: DataSetTypes, DataStoreTypes, TenantTypes
```

## Three-Phase Registration Pattern

All TypeCollections follow a three-phase registration pattern:

### Phase 1a: Configure (Before Build)

Binds `IOptions<T>` for configuration. Call before `builder.Build()`.

```csharp
// Binds configurations from IConfiguration
DomainTypes.Configure(services, configuration, loggerFactory);
```

### Phase 1b: Register (Before Build)

Registers services with the DI container. Call before `builder.Build()`.

```csharp
// Registers providers, factories, and infrastructure services
DomainTypes.Register(services, loggerFactory);
```

### Phase 2: Initialize (After Build)

Resolves services and performs runtime initialization. Call after `builder.Build()`.

```csharp
var app = builder.Build();

// Eagerly resolves provider, loads configurations, validates setup
DomainTypes.Initialize(app.Services, loggerFactory);
```

## Registration Order

Service domains have dependencies. Register in this order:

1. **SecretManagers** - No dependencies
2. **Connections** - Depends on SecretManagers
3. **Authentication** - Depends on Connections
4. **Pipelines/ETL** - Depends on Connections, Authentication
5. **Data (DataSets, DataStores)** - Depends on Connections

## Anti-Patterns: What NOT to Do

### Don't Use ConfigurationLoader Directly

```csharp
// WRONG - Using ConfigurationLoader in entry point
var loader = new ConfigurationLoader(...);  // Now internal
await loader.LoadAll();

// CORRECT - Use TypeCollection pattern
DataSetTypes.Configure(services, configuration, loggerFactory);
DataSetTypes.Register(services, loggerFactory);
DataSetTypes.Initialize(app.Services, loggerFactory);
```

### Don't Skip Phases

```csharp
// WRONG - Skipping Configure phase
DataSetTypes.Register(services, loggerFactory);
DataSetTypes.Initialize(app.Services, loggerFactory);  // IOptions not bound!

// CORRECT - All three phases in order
DataSetTypes.Configure(services, configuration, loggerFactory);
DataSetTypes.Register(services, loggerFactory);
DataSetTypes.Initialize(app.Services, loggerFactory);
```

### Don't Register Providers Manually

```csharp
// WRONG - Manual provider registration outside TypeCollection
services.AddSingleton<IDataSetProvider, DataSetProvider>();

// CORRECT - Let TypeCollection manage registration
DataSetTypes.Register(services, loggerFactory);  // Registers provider
```

## Creating New Configuration Registries

When creating a new configuration registry (MutableTypeCollection pattern):

1. **Create the configuration class** implementing `IGenericConfiguration`
2. **Create the provider interface** (e.g., `IFooProvider`)
3. **Create the provider implementation** (e.g., `FooProvider`)
4. **Create the MutableTypeCollection** with Configure/Register/Initialize
5. **Add to entry point registration** in correct order

Use the `/register-provider` Claude Code skill to automate this process.
