# Getting Started with FractalDataWorks

This is a day-one walkthrough for someone meeting FDW for the first time: install the packages,
bootstrap an app with the three-phase service lifecycle, reach a real data store through
`IDataGateway`, and (as a stretch) see where pipelines fit once you outgrow a single query.

It assumes .NET 10 and a SQL Server instance you can point a connection at. Every type and method
named below is real — resolve it in your IDE against the packages you install; nothing here is
aspirational.

## 1. What you're installing

FDW ships as many small NuGet packages rather than one big framework assembly — you reference only
the pieces your app actually uses. For this walkthrough you need:

| Package | What it gives you |
|---|---|
| `Fdw.Abstractions` | Core marker interfaces (`IGenericService`, `IGenericConfiguration`, etc.) |
| `Fdw.Results` | `GenericResult` / `GenericResult<T>` — the concrete `IGenericResult` implementation |
| `Fdw.Collections` | `[TypeCollection]` / `[ServiceTypeCollection]` base classes and attributes |
| `Fdw.Collections.SourceGenerators` | Generates the `Configure`/`Register`/`Initialize` bodies on your `[ServiceTypeCollection]` partial classes (analyzer-only reference) |
| `Fdw.Commands.Data` | `QueryCommand<T>` and friends, plus the `DataQuery.From<T>(...)` fluent builder |
| `Fdw.Services.Data` | `IDataGateway`, `DataGatewayTypes`, `AddConfigurationGateway(...)` |
| `Fdw.Services.Connections.MsSql` | `MsSqlConnectionFactory` and the MsSql connection type |
| `Fdw.Services.SecretManagers.EnvironmentVariable` | `EnvironmentVariableSecretManager` (resolves secrets from `FDW_SECRET_*` env vars) |

```bash
dotnet new console -n Reference.QuickStart
cd Reference.QuickStart

dotnet add package Fdw.Abstractions
dotnet add package Fdw.Results
dotnet add package Fdw.Collections
dotnet add package Fdw.Collections.SourceGenerators
dotnet add package Fdw.Commands.Data
dotnet add package Fdw.Services.Data
dotnet add package Fdw.Services.Connections.MsSql
dotnet add package Fdw.Services.SecretManagers.EnvironmentVariable
dotnet add package Microsoft.Extensions.Hosting
```

The `Fdw.Collections.SourceGenerators` package is referenced as an analyzer — it doesn't ship
runtime code, it emits the `Configure`/`Register`/`Initialize` static methods you call in step 2.
Every FDW project that declares its own `[ServiceTypeCollection]` references it the same way; you
won't need to declare your own collection for this walkthrough because the ones you need
(`DataGatewayTypes`, `ConnectionTypes`, `SecretManagerTypes`, `DataStoreProvider`, `DataSetProvider`)
already ship inside `Fdw.Services.Data` / `Fdw.Services.Connections` / `Fdw.Services.SecretManagers`.

## 2. The three-phase bootstrap

Every FDW service type — a connection kind, a secret manager kind, a data-gateway kind — is a
`[ServiceTypeCollection]`. Collections are never wired up with ad-hoc `services.AddSingleton<...>()`
calls; they go through the same three static calls, always in this order, always split around
`Build()`:

```
Configure(builder, loggerFactory)   // Phase 1: bind IOptions sections, before Build()
Register(services, loggerFactory)   // Phase 1: register factories/providers, before Build()
------------------------------------------------- builder.Build() -------------------------------
Initialize(services, loggerFactory) // Phase 2: post-Build wiring, after Build()
```

This is generated by `ServiceTypeCollectionGenerator` onto every `[ServiceTypeCollection]` partial
class — see `Configure<TBuilder>(TBuilder, ILoggerFactory?)`, `Register(IServiceCollection,
ILoggerFactory?)`, and `Initialize(IServiceProvider, ILoggerFactory?)` on
`Fdw.ServiceTypes.IServiceType` (`Fdw.Services.Abstractions/IServiceType.cs`). You never call these
three methods yourself for a *new* collection in this walkthrough — you call them for the
collections FDW already ships, in the order the framework's own reference apps use them.

Here is a minimal `Program.cs` — a console host, not a web app, because `Configure<TBuilder>` is
generic over `IHostApplicationBuilder`, not `WebApplicationBuilder`:

```csharp
using Fdw.Services.Connections;
using Fdw.Services.Connections.MsSql;
using Fdw.Services.Data;
using Fdw.Services.SecretManagers;
using Fdw.Services.SecretManagers.EnvironmentVariable.Services;
using Microsoft.Extensions.DependencyInjection;
using Microsoft.Extensions.Hosting;
using Microsoft.Extensions.Logging;

var builder = Host.CreateApplicationBuilder(args);
builder.Logging.AddConsole();

var loggerFactory = LoggerFactory.Create(b => b.AddConsole());

// ------------------------------------------------------------------
// Bootstrap: this is the ONE thing every FDW entry point does first.
// configurationSchema.json declares just enough to reach ConfigurationDb:
// the connection to it, and the secret manager that resolves its password.
// Everything else (other connections, datastores, pipelines, schedules...)
// is a row INSIDE ConfigurationDb, read later through the domain providers.
// ------------------------------------------------------------------
builder.Services.AddConfigurationGateway<MsSqlConnectionFactory, EnvironmentVariableSecretManager>(
    "configurationSchema.json");

// ------------------------------------------------------------------
// Phase 1: Configure + Register (before Build())
// ------------------------------------------------------------------
DataGatewayTypes.Configure(builder, loggerFactory);
DataGatewayTypes.Register(builder.Services, loggerFactory);

SecretManagerTypes.Configure(builder, loggerFactory);
SecretManagerTypes.Register(builder.Services, loggerFactory);

ConnectionTypes.Configure(builder, loggerFactory);
ConnectionTypes.Register(builder.Services, loggerFactory);
ConnectionTypes.RegisterAdditionalInterfaces(builder.Services);

DataStoreProvider.Configure(builder, loggerFactory);
DataStoreProvider.Register(builder.Services, loggerFactory);

DataSetProvider.Configure(builder, loggerFactory);
DataSetProvider.Register(builder.Services, loggerFactory);

var app = builder.Build();

// ------------------------------------------------------------------
// Phase 2: Initialize (after Build())
// ------------------------------------------------------------------
SecretManagerTypes.Initialize(app.Services, loggerFactory);
ConnectionTypes.Initialize(app.Services, loggerFactory);
await DataStoreProvider.Initialize(app.Services, loggerFactory);
DataSetProvider.Initialize(app.Services, loggerFactory);

// ... app.RunAsync() / your own code — see step 4 below
```

This is the same sequence `Reference.Api`'s `Program.cs` runs (it just runs many more domains after
it) — see `reference-api/public/src/Reference.Api/Program.cs`. `DataStoreProvider` and
`DataSetProvider` are registered here even though this walkthrough only queries one table, because
`IDataGateway`'s implementation (`DataGatewayService`) takes both a
`DataStoreConfigurationProvider` and a `Lazy<IDataSetConfigurationProvider>` as required
constructor dependencies — they resolve DataStore/Container metadata and DataSet federation
respectively, and the gateway can't be constructed without them.

## 3. Declare a connection in `configurationSchema.json`

Every FDW entry-point app ships a `configurationSchema.json` next to its executable
(`CopyToOutputDirectory=PreserveNewest`) that bootstraps exactly the connection(s), secret
manager(s), and data store(s) needed to reach ConfigurationDb. Add this file to your project:

```json
{
  "ConfigurationSchema": {
    "Connections": [
      {
        "Name": "ConfigurationDb",
        "ServiceOptionType": "MsSql",
        "Configuration": {
          "Server": "localhost",
          "Database": "ConfigurationDb",
          "Port": 1433,
          "AuthenticationType": "SqlAuth",
          "TrustServerCertificate": true,
          "Properties": {
            "Username": "fdw_config",
            "SecretManagerName": "EnvSecrets",
            "SecretKeyName": "CONFIG_PASSWORD"
          }
        }
      }
    ],
    "SecretManagers": [
      {
        "Name": "EnvSecrets",
        "ServiceOptionType": "EnvironmentVariable",
        "Configuration": {
          "Prefix": "FDW_SECRET_"
        }
      }
    ],
    "DataStores": [
      {
        "Name": "ConfigurationDb",
        "TypeId": "MsSql",
        "Paths": [
          {
            "Name": "agent",
            "Path": "agent",
            "PathType": "DatabasePath",
            "Containers": [
              {
                "Name": "AgentAction",
                "ContainerType": "Table",
                "Fields": [
                  { "Name": "AgentActionId", "Ordinal": 1, "DataType": "int", "IsNullable": false },
                  { "Name": "AgentKeyId", "Ordinal": 2, "DataType": "int", "IsNullable": false },
                  { "Name": "AgentLabel", "Ordinal": 3, "DataType": "nvarchar", "IsNullable": false },
                  { "Name": "UserId", "Ordinal": 4, "DataType": "nvarchar", "IsNullable": false },
                  { "Name": "Route", "Ordinal": 5, "DataType": "nvarchar", "IsNullable": false },
                  { "Name": "Method", "Ordinal": 6, "DataType": "nvarchar", "IsNullable": false },
                  { "Name": "RequestBody", "Ordinal": 7, "DataType": "nvarchar", "IsNullable": true },
                  { "Name": "Status", "Ordinal": 8, "DataType": "nvarchar", "IsNullable": false },
                  { "Name": "RequestedAt", "Ordinal": 9, "DataType": "datetimeoffset", "IsNullable": false },
                  { "Name": "ReviewedAt", "Ordinal": 10, "DataType": "datetimeoffset", "IsNullable": true },
                  { "Name": "ReviewedBy", "Ordinal": 11, "DataType": "nvarchar", "IsNullable": true }
                ]
              }
            ]
          }
        ]
      }
    ]
  }
}
```

Set `<CopyToOutputDirectory>PreserveNewest</CopyToOutputDirectory>` on the JSON file in your
`.csproj`, and set the DB password via the environment variable the schema names:

```bash
export FDW_SECRET_CONFIG_PASSWORD='your-password-here'
```

`AddConfigurationGateway<TConnectionFactory, TSecretManager>(path)` (in
`Fdw.Services.Data/Extensions/ConfigurationGatewayExtensions.cs`) reads this file with
`System.Text.Json` (not `IConfiguration` binding — that's what lets `ServiceOptionType: "MsSql"`
dispatch to the concrete `MsSqlConnectionConfiguration` subtype) and registers the resulting
`ConfigurationSchema` plus `IConfigurationGateway` as singletons.

This walkthrough queries `agent.AgentAction` — a table FDW's `Fdw.Services.Agents` domain already
owns — specifically because its container is declared above with real field metadata, so you can
run the query in step 4 against a live ConfigurationDb with zero additional table setup. A
DataStore you invent yourself (its own Paths/Containers/Fields) is declared the same way, but as
*rows inside ConfigurationDb* rather than in this bootstrap file — see the `configuration-overview`
skill for the read/write path once you're past this walkthrough.

## 4. Run a query through `IDataGateway`

`IDataGateway` is the one path to any backend. A command never carries its own address — the
`DataStoreTarget` (or `DataSetTarget`) travels alongside it into `Execute<T>`:

```csharp
public interface IDataGateway
{
    Task<IGenericResult<T>> Execute<T>(IDataCommand command, DataStoreTarget target, CancellationToken cancellationToken = default);
    Task<IGenericResult<T>> Execute<T>(IDataCommand command, DataSetTarget target, CancellationToken cancellationToken = default);
    // ... OpenRecordSource, BeginTransaction
}
```

(`Fdw.Services.Data.Abstractions/IDataGateway.cs`)

The `DataQuery.From<T>(dataStoreName, pathName, containerName)` fluent builder (`Fdw.Commands.Data`,
namespace `Fdw.Commands.Data`) builds both the command and its `DataStoreTarget` together and
returns a `DataGatewayCall` you can pass straight to `Execute`:

```csharp
using Fdw.Commands.Data;
using Fdw.Services.Data.Abstractions;

public sealed class AgentActionRecord
{
    public int AgentActionId { get; set; }
    public int AgentKeyId { get; set; }
    public string AgentLabel { get; set; } = string.Empty;
    public string UserId { get; set; } = string.Empty;
    public string Route { get; set; } = string.Empty;
    public string Method { get; set; } = string.Empty;
    public string? RequestBody { get; set; }
    public string Status { get; set; } = "Pending";
    public DateTimeOffset RequestedAt { get; set; }
    public DateTimeOffset? ReviewedAt { get; set; }
    public string? ReviewedBy { get; set; }
}

// ... after Initialize() in step 2 ...
var gateway = app.Services.GetRequiredService<IDataGateway>();

var command = DataQuery.From<AgentActionRecord>("ConfigurationDb", "agent", "AgentAction")
    .Where("Status", "Pending")
    .OrderByDescending("RequestedAt")
    .Build();

var result = await gateway.Execute<IEnumerable<AgentActionRecord>>(command);

if (!result.IsSuccess)
{
    Console.WriteLine($"Query failed: {result.CurrentMessage}");
    return;
}

foreach (var action in result.Value!)
{
    Console.WriteLine($"[{action.AgentActionId}] {action.Method} {action.Route} — {action.Status}");
}
```

This is the same shape production code uses — see `Fdw.Services.Agents/AgentActionService.cs`:

```csharp
var builder = DataQuery.From<AgentActionRecord>("ConfigurationDb", "agent", "AgentAction");
if (!string.IsNullOrWhiteSpace(status))
{
    builder = builder.Where("Status", status);
}
var command = builder.OrderByDescending("RequestedAt").Build();
var result = await _gateway.Execute<IEnumerable<AgentActionRecord>>(command, cancellationToken);
```

Notice the shape of failure handling: `result.IsSuccess` is checked, never a `try`/`catch` around
the call, and a failure carries `result.CurrentMessage` rather than throwing. That's
`IGenericResult` — the return type for anything in FDW that can fail (`Fdw.Abstractions/../
IGenericResult.cs` in `Fdw.Results.Abstractions`). Nothing above returns `null` for "not found" or
throws for an expected failure.

`QueryCommandBuilder<T>` (what `DataQuery.From<T>` returns) also supports `Join`, type-safe
`Where(x => x.Property)` with comparison operators, `Paging(skip, take)`, and `WithCaching(...)` —
see `Fdw.Commands.Data.Extensions/QueryCommandBuilder.cs` for the full fluent surface. `InsertCommand`,
`UpdateCommand`, and `DeleteCommand` exist alongside `QueryCommand` in `Fdw.Commands.Data` and are
executed through the same `IDataGateway.Execute` — see the `data-commands` skill for the full set.

## 5. Stretch goal: where a pipeline fits

Once a single ad-hoc query isn't enough — you want a repeatable Extract → Transform → Load run,
possibly on a schedule — that's a **Pipeline**, a named, versioned configuration record (not a
class you author and compile). A pipeline is created the same way any other FDW configuration is:
as a row, through its domain's API/provider, not by writing a `MyPipeline : IPipeline` subclass by
hand.

The pieces involved, all real and shipped in this release:

- `Fdw.Services.Pipelines` — `PipelineServiceTypes` (the three-phase collection for the pipeline
  domain) and `IPipeline` / `IPipelineTypedConfiguration` (`Fdw.Services.Pipelines.Abstractions`)
  define what a pipeline *is*.
- `Fdw.Services.Etl` — pipeline *kinds* (e.g. `StreamingPipelineType` in
  `Fdw.Services.Etl/Pipelines/StreamingPipelineType.cs`) that actually execute steps against
  `IDataGateway`.
- `Fdw.Services.Scheduling` — `SchedulerTypes` and trigger kinds (Cron/Interval/Once/Manual) that
  fire a pipeline run unattended.

In a reference app, a pipeline is defined by calling the pipeline endpoints (or the
`PipelineServiceConfigurationProvider` directly if you're inside the process) with a DataSet
source, transform steps, and a target container — the same `DataStoreTarget`/`DataSetTarget`
addressing you used in step 4 is what a pipeline step resolves against at execution time. There is
no separate "pipeline DSL" to learn: a pipeline is FDW configuration (versioned, validated,
queryable) whose steps are themselves `IDataGateway` calls.

For the full onboarding sequence — connection → datastore path/container/fields → dataset →
pipeline → trigger — see the `etl-transform` skill and the ETL pipeline steps under
`Fdw.Etl.Abstractions` / `Fdw.Services.Etl`. That is genuinely more surface than a getting-started
doc should inline; the mechanism you now understand (three-phase bootstrap, `IDataGateway`,
`IGenericResult`) is the same mechanism the pipeline domain builds on, not a different one.
