## [Unreleased]

### Breaking
- A pipeline's description, and its parameters', are kept in the descriptions table and no longer in `pipe.GraphPipelineConfiguration.Description` and `pipe.PipelineParameter.Description` (FDW-7323, a group of FDW-6208), and the stored script's, the webhook trigger's and the orchestration node's likewise (`pipe.SqlScriptConfiguration`, `pipe.WebhookTriggerConfiguration`, `pipe.OrchestrationNodeConfiguration`); the unused `pipe.Pipeline.Description` column is dropped with its texts printed first. `IPipelineImplementationConfiguration.Description` has a setter and the interface has a new member `DescribedParameters` (`IReadOnlyList<IDescribedPipelineParameter>`, new in `Fdw.Services.Pipelines.Abstractions`): **a class that implements the interface by hand must add both**. `PipelineServiceConfigurationProvider`, `ScriptConfigurationProvider`, `WebhookTriggerConfigurationProvider` and `OrchestrationNodeConfigurationProvider` take an `IDescriptionWriter` and an `IDescriptionReader` as their last two constructor parameters; every pipeline type option and pipeline service option requires `IDescriptionWriter` (`PIPELINES-60860`, `PIPELINES-60861`), so a host that registers the pipeline types registers the Descriptions service type. The saved text of a graph pipeline and a graph's parameters is written in the unit of the save, and a graph saved with no text removes the one it had.
- The Description columns of `sec.Identity`, `sec.ClientCredentialsIdentityConfiguration`, `sec.JwtAssertionIdentityConfiguration`, `sec.SecretManager` and `sec.HashiCorpVaultSecretManagerConfiguration` are gone, and those of `sec.CredentialService`, `sec.DataVault` and `sec.ExternalIdentityProvisioner` with them (FDW-6208, FDW-7257); `sec.Secret` keeps its column, because it is the MsSql secret manager's own storage, not a configuration record. An identity's text lives in `catalog.Description` under the new type `Identity` (no owner, `identities:read`, whichever mechanism's typed body carries it) and a secret manager's under `SecretManager` (no owner, `system:admin`, the policy its routes ask). **These domains never fill a record on load** (the descriptions domain reads the settings and the caller's authentication, so a fill would loop): a record read through `IdentityServiceConfigurationProvider` or `SecretManagerConfigurationProvider` carries a null `Description`, and a save that states none keeps the stored text, a non-blank text is written and a stated blank removes it. **`IdentityServiceConfigurationProvider` and `SecretManagerConfigurationProvider` take an `IDescriptionWriter`** (a last constructor parameter; anyone who builds them by hand passes it), `IdentityServiceTypes` and `SecretManagerTypes` require it at Initialize (IDENTITY-60390, SECRETMGR-60391: a host that registers them without the Descriptions service type stops with that message; the Aegis MCP host registers it now, aefca76ca1), `IIdentityServiceImplementationConfiguration` now extends the new `IDescribedConfiguration` (`string? Description { get; set; }`, in `Fdw.Abstractions`; a secret manager body states a text by implementing it), and `GetSecretManagerEndpointBase` takes an `IDescriptionReader` (its constructor gains it) and shows the text by one read. `Fdw.Services.Identity`, `Fdw.Services.SecretManagers` and `Fdw.Services.SecretManagers.Endpoints` reference `Fdw.Services.Descriptions.Abstractions`. `sec.CredentialService`, `sec.DataVault` and `sec.ExternalIdentityProvisioner` have no member, route, view or reader for their description, so their text goes with the column (the migration prints it first). **Breaking for host DDL**: a host's `configurationSchema.json` drops the field from the eight containers (reference-api, reference-etl and reference-scheduler do) or it fails its first read of them; a database that keeps its data runs `FDW-6208-sec.sql` first (databases `scripts/migrations`), on every database of an app on slots. Saving a secret manager or an identity with a text on a host that states no `DescriptionLanguage` fails with `DescriptionLanguageNotStated` and writes nothing; saving without a text works.
- `DomainServiceProviderBase` has a new abstract member `ReadOptions` (`ConfigurationReadOptions`, protected, FDW-7354; FDW-7351 had it virtual). **A class that derives from the base must state it**: `WithoutFilledMembers` when the service it builds never shows the configuration's description and never saves it back (`ConnectionProvider`, `NotificationServiceProvider`), `Whole` otherwise. Why: a service provider that does not decide would read as every read did; the choice is the provider's. Every provider of this repository states it (ten more: language models, external identity, identity, secret managers, credentials, data vault, scheduler, health monitor, ETL pipeline, `DefaultServiceProvider`).
- The Description columns of `quality.QualityRuleConfiguration`, `quality.QualityRuleReferenceValue`, `catalog.DataSetAnnotationConfiguration` and `catalog.DataSetAnnotationFieldDescription` are gone, and `dg.DataGateway`'s with them (FDW-6208). A quality rule's text and each reference value's live in `catalog.Description` under the new types `QualityRule` and `QualityRuleReferenceValue` (owned by its rule, `quality/rules:read`); an annotation's text and each field description's under `DataSetAnnotation` and `DataSetAnnotationField` (owned by the annotation, `datastores:read`). **`QualityRuleConfigurationProvider` and `DataSetAnnotationConfigurationProvider` take an `IDescriptionWriter` and an `IDescriptionReader`** (after their container name; anyone who builds them by hand passes them), and `DefaultQualityServiceType` requires the writer (a host without the Descriptions service type stops at Initialize with QUALITY-60349). `Fdw.Services.Quality` now references `Fdw.Services.Descriptions` and `Fdw.Services.Descriptions.Abstractions`. `dg.DataGateway` has no record member, route, view or reader for its description, so its text goes with the column and moves nowhere (the migration prints it first). **Breaking for host DDL**: a host's `configurationSchema.json` drops the field from the five containers (reference-api, reference-etl and reference-scheduler do) or it fails its first read of them; a database that keeps its data runs `FDW-6208-quality.sql`, `FDW-6208-annotation.sql` and `FDW-6208-dg.sql` first (databases `scripts/migrations`), on every database of an app on slots. No route loses a description.
- The `Description` column is removed from `workflow.Workflow`, `workflow.EscalationPolicyConfiguration` and `workflow.ThresholdConfiguration` (FDW-7205, a group of FDW-6208). An escalation policy's and a threshold's description lives only in `catalog.Description` under the description types `EscalationPolicy` (`escalation:read`) and `Threshold` (`thresholds:read`), and the records' `Description` member is filled from it on every read, so every route that returned one still returns it. `EscalationConfigurationProvider` and `ThresholdConfigurationProvider` take `IDescriptionWriter` and `IDescriptionReader`, and the operations service type refuses a host that did not register the Descriptions service type (`OPERATIONS-60348`); the escalation alert engine, which reads the policies with no signed-in caller, needs `DescriptionLanguage` stated at the server scope, as the upgrade requirement above says. `workflow.Workflow` has no record, route or reader, so its column goes with its text and nothing moves. `FDW-6208-workflow.sql` copies the two texts and drops the columns when the count agrees, and prints every text of `workflow.Workflow` and the count before it drops that column; a host that declares one of the three tables regenerates its `configurationSchema.json`.
- **`SchedulerBackgroundServiceBase.Evaluate` answers `Task<IGenericResult>`, not `Task`** (FDW-7285). A pass that could not do what it set out to (a schedule load that failed, for one) answers a failure carrying the cause; the loop logs it at Error through `SchedulerLoopLog.EvaluationNotCompleted` (event 549) with the cause's code and does not log the completed-pass line (`EvaluationCompleted`) for it; the delay and the next pass after `EvaluationInterval` are unchanged. A class that overrides `Evaluate` returns `GenericResult.Success()` for a pass that finished and the cause's failure otherwise. In this repository and reference-servicetypes the only overrides were `QuartzReconciliationService` and the loop test's double, both changed.
- The Description columns of `data.DataConfigurationRule` and `data.DataConfigurationRuleValue` are gone (FDW-6208): a data option rule's description and each value's live only in `catalog.Description`, under the new description types `DataConfigurationRule` (no owner) and `DataConfigurationRuleValue` (owned by its rule), both read with `datastores:read`. **`DataConfigurationRuleService` takes an `IDescriptionWriter` and an `IDescriptionReader`** (after `IDataStoreProvider`; the container resolves them, anyone who builds the service by hand passes them). The service describes the rule and its values in the same `ConfigurationWriteScope` as their rows and the audit record, so a description that cannot be written rolls the write back, and fills both members from the table once for every page it reads; no route loses a description. **Breaking for host DDL**: a host's `configurationSchema.json` drops the field from the two containers (reference-api, reference-etl and reference-scheduler do) or it fails its first read of them; a database that keeps its data runs `FDW-6208-rules.sql` first (databases `scripts/migrations`), on every database of an app on slots.
- A run can ask its person to answer and end, and the person's answer starts the continuation once (FDW-6142). New component `Ask` (`AskComponentType`, a decision with outputs `go` and `asked`; settings `policy`, `call`, `kind`, `continuation`, `answerParameter`, `rule`, `title`, `body`, `options`, `grantVariable`, `parameters`): it judges a call under an answer policy (`IAnswerPolicies`: `pipe.AnswerPolicy` states `ExpiresAfterSeconds`, `pipe.AnswerPolicyCall` states per call one of `AnswerPolicyRequirements` Automatic, Refused, NeedsPerson, GrantOrPerson, and the outcome is one of `AnswerPolicyOutcomes`: Automatic, WouldBeRefused, NeedsPerson, Granted; a call a policy does not list is refused, and a stored grant `IRunGrants` that has ended, was revoked or does not allow the permission leaves a grant-or-person call to the person). A call that needs the person keeps an answer request (`IAnswerRequests.Ask`, the rows `etl.PipelineAnswerRequest` with `Shown`, `Argument` and `Role` children, `AnswerRequestKinds` Question and Choice, `AnswerRequestStates` Keeping, Open, Answered, Started, Expired), tells the person with a Card payload through the stated notification rule and fires only `asked`. Exactly once is held by the store: a unique key on (tenant, chain root, component, iteration) refuses a second request for a step, the answer is one conditional update (`Open`, the caller's, not past `ExpiresAt`) judged by the rows it changed, and the continuation's start is claimed under the asking run's chain (`IPipelineStepClaims`) before `IPipelineRuns.Start` is called as the caller, with the saved arguments, roles and the answer; a start that failed, or never recorded how it ended, is not made again. What the person is shown and the continuation's arguments are kept with the request, never taken from the answer call (`POST /answer-requests/{Id}/answer` states the text and nothing else; `GET /answer-requests` lists the caller's open requests; both under the new permission `pipelines:answer`). An Ask needs both its outputs drawn, as every decision does (an output nothing reads is refused at save): its author draws `asked` to what the person is told next and `go` to the call. Known limits of 1.6.0: a request can expire but starts nothing when it does, and a request cannot be withdrawn. Database: four OpsDb tables and two ConfigurationDb tables, `scripts/migrations/FDW-6142.sql` and `FDW-6142-answer-policy.sql` for a database that keeps its data, and the policy tables are declared in the three hosts' `configurationSchema.json`.
- The `Description` column is removed from `otel.Telemetry`, `hlth.HealthMonitor`, `rsl.ResiliencyPolicy`, `crs.Cors` and `cred.CredentialStore` (FDW-7204, a group of FDW-6208), and its text goes with it: no record loaded from these tables has a `Description` member, no route, view or reader shows it (nothing loads or writes `rsl.ResiliencyPolicy`: its only provider is `EmptyResiliencyPolicyProvider`), so nothing moves to `catalog.Description`. `FDW-6208-runtime-options.sql` prints every non-blank text and the count before it drops the column, and a second run prints 0; a host that declares `hlth.HealthMonitor` or `rsl.ResiliencyPolicy` regenerates its `configurationSchema.json`.

The text lives only in `catalog.Description` under the new description types `ServerSetting` (`settings/server:read`), `Theme` (`configurations:read`), `AuthenticationFlow` and `TokenManager` (`settings/server:read`), none with an owner. **These four are never filled on load**: the record's `Description` stays, `[NotStored]`, `string?` with no initializer, and is `null` after a read, because the description service reads the language through the server settings (a filled read of a setting would read the setting it is reading), a flow is read at sign-in and a token manager when a token is issued. So `null` means "nothing was said": a save of a loaded record keeps the stored text, a non-blank text is written in the unit of the save, a blank text removes it (`IDescriptionWriter.DescribeWhenStated`, a new extension in `Fdw.Services.Descriptions`, writes only the first two cases of `Describe`). Constructors changed: `ServerSettingConfigurationProvider` takes `Lazy<IDescriptionWriter>` (registered beside `Lazy<IEffectiveSettingsProvider>`, FDW-3284: the description service reads the language through the effective settings, which read through that provider), `ThemeConfigurationProvider`, `AuthenticationFlowConfigurationProvider` and `TokenManagerConfigurationProvider` take `IDescriptionWriter`, `InheritedSettings`, `AuthenticationFlowAdministration` and the three server setting endpoint bases take `IDescriptionReader`; `ITokenManagerImplementationConfiguration` gains `Description`. `SettingsServiceTypes` and `AuthenticationStepTypes` refuse a host that did not register the Descriptions service type (`SETTINGSDESC-60383`, `AUTHFLOWDESC-60384`). `FDW-6208-settings-auth.sql` copies the texts, counts, then drops the four columns; a host that declares one of the four tables regenerates its `configurationSchema.json`. **Upgrade requirement:** a route that shows one of these texts needs the description language, so a host whose server setting `DescriptionLanguage` is not stated fails those routes (seed 64 states `en-US`); the loads themselves (sign-in, token issuance, the theme at start) read no description and need none.
- The person a run is for follows it piece by piece and resumes after a dropped connection (FDW-6140). New OpsDb table `etl.PipelineRunStream` (upgrade script `FDW-6140.sql`); its row id is the sequence. `IRunStream` (`Write`, `ReadAfter`), `RunStreamKinds` (`Text`, `StepStarted`, `StepEnded`, `StepSkipped`), `RunStreamPiece` and `IRunAudience` (who may follow besides the person; a host that registers none lets the person alone follow). `FlowSequence` writes `StepStarted` and `StepEnded` around every step, and `FlowActionComponent` writes `StepSkipped` when no line that leads to it fired (`FLOW-21036`); a step that has text writes it through `FlowStepContext.Stream`; a piece that cannot be kept fails the step, never goes missing. A run that acts as no person writes nothing. Reading: `ReadAfter(tenant, person, claimRootId, afterSequence, take)` answers the pieces after the sequence in order, at most the new setting `RunStreamPageSize`; another person gets `PIPERUNSTREAM-40850` and no piece. Pieces older than the new setting `RunStreamRetentionSeconds` are removed as the next step starts. Both settings are required (seeded 200 and 86400 in `08-seed-baseline-runtime.sql`): while one is not set the stream is not written or read (`60855`). The route `GET /pipeline-runs/{ExecutionId}/stream` (`FollowPipelineRunEndpointBase`, `pipelines:read`) is in reference-servicetypes. `FlowStepContext` takes an optional `IRunStream`, `GraphPipeline` and `GraphPipelineFactory` an optional `IRunStream`. Each piece written is also pushed: `IPipelineStatusBroadcaster.BroadcastRunPiece(PipelineRunPieceUpdate)` (**a class that implements it by hand must add the member**; the relay broadcaster, the routing one and the hub's own do) reaches the hub through the relay's new event kind `RunPiece` and is sent as `OnRunPiece` to the group of the person it is addressed to, `HubScopes.User(person)`, which `PipelineStatusHub` now joins on connect from the connection's own `sub` claim; the piece carries its `sequence`, so a console that connects or reconnects calls the stream route with its last sequence to replay, takes the pushes, and drops any sequence it holds; after a run's completion it replays once more from its last sequence, because a push is best effort (a push that fails is a warning, `PIPERUNSTREAM-70856`, and the piece is kept). The delay a person sees is the relay's own interval: `RelayFlushMilliseconds`, declared on the pipeline hub option with a default of 500 ms (and `RelayBufferCapacity` 1000, which only ever drops components updates, never a piece). A person shared with through an `IRunAudience` is not pushed to: they read the stream route. ### Fixed
- A page of domain records no longer fills the rows the gateway cached (FDW-7326). `Get(DomainQuery)` handed the cached rows, the same objects for every caller of the query, to the domain read observers, which write the description into them; a text removed afterwards stayed on the cached row until the entry expired. The page now copies each row through the row mapper (`new TDomain()` and `SetValue` over `MapToParameters`) and fills the copies. Affected: the categories, data stores, data set variation lists, calculations and calculation versions lists. An implementation record was already a per-read copy (`ImplementationProviderBase`).
- A connection's cursor over a query that joins or stacks containers reads the columns the query returns (FDW-6970). New `CursorFields.Of(command, container, logger)` (`Fdw.Services.Connections`) gives the fields a cursor builds its records over: the container's own data fields for a read of one container, and each projected column under its alias for a query with joins or unions. Before, a cursor was built over the container the query is sent to, so a pushed join lost its joined side's columns. A combined query that states no projection is refused with `CONNECTIONS-22820`, and a column with no alias with `CONNECTIONS-22821`. The reference SQL Server, PostgreSQL and SQLite connections build their cursors over it.
- The data configuration rule service answers from the write, not from a read kept before it (FDW-7248): it read the rule again right after every write, but its write was a raw transaction whose commit dropped none of the gateway's cached reads, so with the gateway's cache on, a data option rule route that removed, restored, changed or added a rule could answer the rule as it was before the write, and later reads could be stale until the cache expired. Every write now commits through a `ConfigurationWriteScope`, which drops the cached reads of the rule table and the value table after the commit (a failed write drops none). Tests: `ARemoveAnswersTheRemovedRuleAndNotTheReadKeptFromBeforeTheWrite`, `AnAddDropsTheCachedReadsOfTheRuleTableAndTheValueTableAfterTheCommitAndAFailedWriteDropsNone`.
- `POST /datasets/graph/validate` lists a display name or an abbreviation longer than its column as a problem at `displayName` or `abbreviation` (`DisplayNameTooLong`, `AbbreviationTooLong`), by the same `DataSetNames.Check` saving runs (FDW-6118). A draft with both too long lists both.
- `PATCH /datasets/{name}` on a Graph data set or a Variation is refused with `ImplementationChangeNotAllowed` (HTTP 400) and writes nothing. The kind a data set's sources make is only Simple, Compound or Federated, and the update moved a Graph data set or a Variation to Simple, dropping what Simple has no place for (FDW-6129, FDW-6117). A Graph data set is updated by `PATCH /datasets/graph/{name}`.

### Breaking: source layout only

- Each domain folder holds a `CLAUDE.md` describing the domain (its projects, seams, rules, tests and dependencies), in no package. They are written by `public/tools/reorg/gen_domain_guides.py`, and `public/.gitignore` un-ignores exactly those 42 files.

## [1.4.4] - 2026-10-30

Released with reference-servicetypes 1.4.4 and the reference servers and console 1.4.4. An application with its own configuration database needs the schema changes listed under Breaking applied before it takes this version. Test-only fixes are not listed, and each entry under Fixed, and each entry that begins Fixed:, describes the fault as it was before 1.4.4; 1.4.4 fixes it.

### Breaking

- The promotion API is removed: every `/promotion` route (environments, requests, approve, reject, compare and execute) answers 404, and the promotion tables in the quality schema, their configuration classes and providers, and the hosts' declarations for them are dropped.
- `PATCH /secret-managers/{name}` takes `{"configuration": {...}}`, the type's own settings, merges them over the stored ones and saves them. A setting the type does not take is refused by name. `Description` and `Environment` are gone from the request; they were never saved.
- `ConditionOperator` is no longer part of the notification rule create API. A rule's severity is one of those `GET /notifications/rules/severities` serves, checked when the rule is saved, with no default.
- `AuiMiddleware` builds the manifest for the signed-in user and answers 401 when nobody is signed in. The reference-aui demo host wires the middleware without authentication, so its manifests answer 401 once it moves to this build.
- The OpenAPI, OData and SQL Server schema importers now register in `SchemaImporters`. The OpenAPI importer refuses a field with no type or no converter (`OpenApiFieldTypeUnknown`) and imports a plain integer as Int64, where it used to import both as string. The OData importer refuses `$metadata` with no `EntityType`.
- `GET /secret-manager-types` requires the platform administrator and names each type's settings container. The reference API references all six secret manager Registration packages, including the new `FdwReferenceSecretManagers.HashiCorpVault.Registration`.
- `GET /search` and `POST /find` are removed from the API.
- Fixed: Four DELETE routes answer 204 for an id that does not exist (annotation by id, glossary term, quality rule, escalation policy).
- Pipeline runs are no longer one at a time across pipelines. The ETL server runs the runs of different pipelines at once, up to `MaxConcurrentPipelineRunsPerServer` and `MaxConcurrentPipelineRunsPerTenant`; runs that write the same table take turns, and a run whose writes cannot be told runs alone. Neither setting has a value in code: an environment whose configuration lacks either row refuses every pipeline run, naming the setting, so every environment needs both before it takes 1.4.4.
- Each pipeline states how many of its runs may run at once (`MaxParallelRuns`, at least 1) and what happens to a run triggered while that many are active (`OverflowBehavior`: `Queue`, the run waits its turn, or `Refuse`, the run ends as failed with reason `RunRefused`.
- A calculation whose DataSet input names a view (a data set made from another data set plus a saved filter, such as AfcQuarterbacks, AfcPlayers filtered to Position = QB) reads that view's rows with its saved filter, as the caller, up to the row cap (`MaxCalculatedFilterRows`), by the same path the `/data` routes use, with rows cut to the data set's declared fields.
- `POST /calculation-entities` and `PATCH /calculation-entities/{id}` answer 400 (ENDPOINTS-21539) for a configuration member the calculation kind does not declare. Formula declares `formulaBody`, `formulaLanguage` and `timeoutSeconds`; Windowed declares `targetField` and `windowFunction`.
- The ETL host's trigger queue size, 100 before, is now the server setting `MaxQueuedPipelineTriggers` (Int32, positive), read once when the host starts. It has no default in code: any host that runs the pipeline trigger queue and whose server settings lack the row does not start, and its log names the setting.
- A calculation whose input is a data set reads that data set's rows as the caller: the data store applies the caller's row-level security through the request's gateway, up to the calculated-filter row cap (the `MaxCalculatedFilterRows` setting for the caller's tenant and role, as `/data` resolves it).
- A pipeline that belongs to the global tenant now reads every tenant's rows, read only, except the system tenant's and rows marked Restricted. Before, the database's row filter left the global tenant out of a run, so such a pipeline over another tenant's data set was accepted and then failed at run time with "Dataset not found"; that reason now names the tenant cause.
- Fixed: PATCH /calculation-entities/{id} with part of a configuration resets the members left out to their defaults.
- `IDomainConfigurationProvider<T>` (Fdw.Services.Abstractions) gains `Update`, typed and untyped: the same write as `Save` except that the record must name an existing member, and it fails as not found (event 31061, UpdateTargetNotFound) when the member's row is gone, or when the record carries an Id that names no member.
- How often a host checks each configuration database for a reset is now the server setting `ResetWatchIntervalSeconds` (Int32, positive), read once when the host starts. It has no value in code: a host that registers settings and finds no positive row does not start, and its log names the setting (event 20988). databases-seed carries it with 10, so a reseeded environment has it.
- Removed with it: `POST /calculation-entities/validate-formula`, `ICalculationApiClient.ValidateFormula` and `GetFunctions`, the Formula step executor, the Fdw.Expressions package, the Formula editor client types and the console's FormulaTokenizer; CALCULATIONS-21024 and CALCULATIONS-21025 are retired.
- Pipeline wait thresholds are new configuration, and every configuration database a host of this version reads must carry it before the host starts: three tables, `pipe.WaitThresholdLevel` (one row per owner that states a level: the server, a pipeline or a schedule, with its mode Inherit, Own or None), `pipe.WaitThreshold` and `pipe.WaitThresholdRule`, declared in every host's `configurationSchema.json`, and the server's level row, which databases-seed writes with mode None (no alert, today's behaviour).
- A pipeline run that has not started (held for a delayed start, waiting its turn, or waiting for approval) is kept in the new operational table `etl.PipelineRunRequest` and survives an ETL host restart; its run values are stored as they are, because a run value is never a secret.
- Each kind of calculation input says which members it takes, and the type-collection values route lists them as its parameters: a DataSet input takes `dataSetName`; a Scalar input takes `scalarValueType` and `scalarSerializedValue`; a Container input takes `connectionName` and `containerPath`.
- `POST /calculations/execute` finds a data set name the way `/data` does, so the name of a view is found; an unknown name still answers 404. `ExecuteCalculationEndpointBase`'s protected constructor takes `IDataSetResolver` in place of `IConfigurationGateway`, so an endpoint that derives from it must pass the resolver (the reference `ExecuteCalculationEndpoint` does).
- A calculation create or update refuses an input that leaves out a member its kind requires, with 400 ENDPOINTS-21548 naming the input's alias, its kind and the member: a DataSet input needs `dataSetName`, a Container input `connectionName` and `containerPath`, a Scalar input `scalarValueType` and `scalarSerializedValue`, each named on its own.
- A Scalar input's value is checked against its type when a calculation is created or updated: a value that is not a value of its type is refused with 400 ENDPOINTS-21549, "Calculation input '<alias>' has scalar value '<value>', which is not a value of type '<type>'".
- A pipeline destination states what it writes, as a source does: `targetKind` File writes one file and Files writes one file per value of the destination's split field, each holding only that value's rows, with the required `truncateFirst` deciding whether an existing file is replaced or added to.
- A connection or secret manager that states no command timeout no longer gets 30 seconds from the code or the column: it takes the required server setting `DefaultCommandTimeoutSeconds`, and is not built where neither is present (SETTINGS-62030 to 62033 name it). The SQL Server, PostgreSQL and SQLite connection columns and the SQL Server and SQLite secret manager columns lose their `DEFAULT 30`. A host's bootstrap connections state their own `CommandTimeoutSeconds` in `configurationSchema.json`.
- A create that used to overwrite a member of the same name now refuses it with a conflict (SERVICES-40001, CreateTargetExists): CreateRole, CreateDataSetAnnotation, CreateQualityRule, CreateEscalationPolicy and BindExternalIdentity. A caller that relied on a create replacing the old member must use the update.

### Added

## [1.0.0-rc.1] - 2026-07-02 — Initial release

This is the first public release of FractalDataWorks (FDW): a .NET framework for building
data-centric services (APIs, ETL pipelines, schedulers, and UIs) on a small set of consistent
mechanisms — a fail-loud result type, extensible-enum TypeCollections, a single data-access
gateway, database-backed configuration, and a render-agnostic UI model. The sections below
describe the framework **as shipped**, not as a diff from an internal pre-release.

### Added

**Results & messaging**
- `IGenericResult` / `IGenericResult<T>` — the universal return type for anything that can fail.
  Methods never return `null` and never throw for expected failure; they return a result carrying
  a `ResultCode`, a message chain, and root-cause tracking (`IsSuccess`/`Value`/`Status`/`CodeChain`/`RootCause`/`IsEmpty`)
- `IGenericMessage` / `GenericMessage` — structured message type (`Message`/`Code`/`Source`/severity),
  produced by the MessageLogging generator rather than hand-built
- Categorized `ResultCode` catalog — every code's number doubles as its `Id` and `EventId`; the
  leading digit selects one of 11 handling categories via the closed `ResultCategories`
  TypeCollection, including `ForbiddenCategory` (403) and `GatewayTimeoutCategory` (504) alongside
  Success/Validation/Auth/Conflict/Dependency/Transient/Configuration/Missing/Internal
- `[MessageLogging]` source generator — `[MessageLoggingTypeCode("PREFIX")]` partial classes with
  `[MessageLogging]` partial methods that both log and return an `IGenericMessage`; raw `ILogger`
  calls are disallowed by analyzer (FDW003)
- `logger ?? NullLogger<T>.Instance` as the one sanctioned fallback pattern in the codebase

**TypeCollections, source generators & analyzers**
- TypeCollections — the framework's extensible-enum mechanism: `[TypeCollection]` families of
  `[TypeOption]` members looked up by `ById`/`ByName`/`All`, auto-registered at module load.
  Failed lookups return a `NotFound` sentinel, never `null`
- ServiceTypeCollections — `[ServiceTypeCollection]` plugin families driving a three-phase DI
  lifecycle (`Configure → Register → Initialize` on the collection; `RegisterRequiredServices` /
  `RegisterFactory` per option). This is the only service-registration mechanism in FDW — no
  ad-hoc `AddXxx` extensions
- Source generators covering configuration DDL + validators, POCO row↔object mappers
  (`[GenerateMapper]`), MessageLogging, TypeCollection/ServiceTypeCollection scaffolding, and
  cross-assembly registration
- FDW001–FDW023 Roslyn analyzer family enforcing the no-fallback/no-raw-logging/TypeCollection/
  ServiceType conventions at build time

**Data access (DataGateway)**
- `IDataGateway` — the only data-access path in the framework. Addressing is supplied per call via
  `DataStoreTarget(DataStore, Path?, Container)` or `DataSetTarget(DataSet)`; commands never carry
  raw connection strings or schema/table strings
- Command set: Query / Insert / BulkInsert / Update / Delete / Find / Truncate, plus DDL commands
  (CreateTable/AlterTable/Index/Schema/View and drops), all reached through `IDataGateway.Execute`
- Gateway-native transactions (`BeginTransaction`) — a scope's calls run on one physical connection
  in one native transaction, with fail-loud behavior when a backend doesn't support transactions
- Streaming cursor (`OpenRecordSource`) for backends that support it, with fallback to materialized
  execution when they don't
- Caching built into the gateway itself — a tag-invalidated result cache gated by configuration,
  with a per-call `useCache:false` escape hatch; no cache decorators or per-provider caches
- Per-connection limit enforcement (rate, concurrency, result size, and query/byte budgets)
- `IConfigurationGateway` — the same gateway model specialized for reading/writing ConfigurationDb

**Connections, SQL dialects & data motion**
- Six connection backends: MsSql, PostgreSql, Sqlite, Http, FileSystem, and RoslynWorkspace, each
  exposing capability marker interfaces so callers never branch on connection type
- A shared SQL translator (`SqlDataCommandTranslatorBase`) plus a per-backend `ISqlDialect`
  (TSql / PlPgSql / Sqlite) — adding a new SQL backend means adding a dialect and a driver, not a
  new translator
- DataSets — a `DataSetTypes` strategy dispatch (Simple / Compound / Federated) so a named DataSet
  resolves to the right execution strategy at runtime
- Pipeline and transform infrastructure: ETL pipeline steps, field-level data transformers, and
  DI-managed transformation services, plus pipeline/task type collections for Extract/Transform/
  Load/Validate/Branch/Notify style orchestration
- Data lineage node/edge/graph model with execution integration

**Configuration**
- `[ManagedConfiguration]` — a class-level attribute that drives DDL generation, validation, and
  UI form metadata for configuration POCOs
- Parent-header + typed-body pattern for polymorphic configuration (e.g. a Connection header with
  one typed body per connection kind), so runtime fields land on the correct table
- One configuration-provider mechanism (`DefaultConfigurationProvider<TConfig,TCommand>`) composing
  reads (`Get(name)/Get(id)/Get()`) and cascading writes (`Save`) with version-on-write and
  tag-based cache invalidation
- App-shipped `configurationSchema.json` — each entry-point app declares the connections,
  secret managers, and data stores it needs to reach its configuration store

**Service domains**
- Connections and SecretManagers (MsSql, Sqlite, Azure Key Vault, environment variable, user secrets)
- Authentication via OpenIddict (OAuth2/OIDC authorization server, RS256 tokens, permission claims
  baked at issuance, client-credentials support)
- Authorization — org-scoped role/permission model enforced through a permission requirement/handler
  pair, with an effective-permission resolver
- Multitenancy — two-level Tenant→Org isolation with tenant-aware connection routing and cache keys
- Health monitoring — a `HealthMonitorTypes` collection with a local health monitor implementation
  and provider
- Scheduling (Cron/Interval/Once/Manual triggers) driving ETL dispatch from a background loop
- Execution/Operations tracking with a validated state machine and escalation policies
- Users/Credentials, DataVault, Quality, Workflows, Notifications (Console/Email/Webhook/System),
  Messaging, Session state, Settings, Audit, Agents, and Resiliency (Polly-backed retry/failover)

**Hosting & UI**
- Hosting middleware: security headers, an internal API key gate for machine-to-machine endpoints,
  forwarded-headers support, fail-loud bootstrap validation, and bounded Serilog flush on shutdown
- Render-agnostic UI — `UI.Abstractions` contracts and an `IUIRenderer` seam, with a Spectre console
  renderer as the reference implementation
- Headless Blazor components — a Context/Provider/ProviderLog triple that keeps logic in
  render-agnostic providers so skins stay presentation-only
- Realtime hubs — a `RealTimeHubBase<TClient>` base plus a `RealTimeHubs` TypeCollection so each
  SignalR hub is registered as a single type option instead of app-specific wiring
- `Fdw.DevSession.Abstractions` — worktree/branch isolation contracts (`IWorktreeEngine`,
  `IIsolationLevel`) for tooling that needs to stage isolated copies of a working tree
